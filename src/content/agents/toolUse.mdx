# Five hands, one English mouth

Tap any of the five cards on the left. Each is a tool the agent can call &mdash; *web_search* for current facts, *calculator* for arithmetic the model shouldn't guess at, *file_read* for local data, *code_exec* for sandboxed scripts, *calendar_create* for the kind of real-world action that has consequences. Below each card's title is the JSON schema for that tool's calls: the names and types of arguments the model must supply, and what it can expect back. The right pane shows what happens when the model decides to use the tool you tapped &mdash; first a short sentence of natural-language reasoning, then the structured call that gets sent to the runtime, then the structured result that comes back to the model. Three panels stacked. One round trip.

The fact that a *language* model can use *tools* at all is, on first encounter, slightly strange. The model has been trained on text. It produces text. How does it call a function? The answer is that calling a function *is* producing text, in a particular format the runtime knows how to parse. When the model emits the string `web_search({ query: "weather Berlin today" })`, the runtime sees a substring that matches a tool-call pattern, peels off the function name and the JSON argument, hands them to a real Python function, gets back a real Python value, serialises that back to JSON, and inserts the serialised result into the model's context. From the model's point of view it is *always* writing text. From the runtime's point of view, some of that text gets intercepted and used to drive real machinery. The interface between the model and the world is, in the most boring way, a string format. The schema is the contract.

This is a more profound design choice than it looks. It means the model doesn't need to be retrained to learn a new tool. You can give it a new tool *at inference time* by extending the prompt with the tool's schema, the way you'd give a colleague a new option by writing it down. (*"Hey, by the way, you also have access to a calendar API; the signature is `calendar_create(title: str, when: ISO8601, with: list[str])`."*) The model reads the new schema, the same way it reads everything else, and starts emitting calls in the new format on the spot. The Toolformer paper from Meta in February 2023 pushed this further: it showed that you could pretrain a model on text that *contained tool calls and their results inline*, and the model would learn the affordance the same way it learned grammar. The model never had a "tool-use module" bolted on; tool use was, for it, just another kind of text it had read enough of to write fluently.

The five tools on the left are a deliberate menagerie, not a random list. Each one represents a different kind of capability and a different shape of risk.

*web_search* is the safest tool you can give an agent: it can read the public web. The blast radius is bounded; the worst case is that the search returns garbage and the model reasons from a wrong starting point. Most agents, today, do most of their work through some variant of this tool plus a *fetch_page* companion. They are, in effect, scripted readers.

*calculator* is the smallest and the most important. The base language model is *not good at arithmetic*. It will confidently tell you that 17 × 19 is 313 (it's 323). The model is bad at it because the model has no place to *do* the multiplication; it has to guess the right next token directly. A calculator tool, even a tiny one, takes the model from "guesses arithmetic" to "delegates arithmetic." The right answer to *what's the temperature difference in Fahrenheit?* is for the model to write the conversion formula in English, hand the numbers to the calculator, and read back the result. The model becomes correct by *deferring* to a thing that was already correct.

*file_read* is the bridge to the user's own data. A research agent can read the user's notes. A coding agent can read the user's repo. The risk is privacy: the model now has access to material the user might not have intended it to read. Production agents lock this down with explicit per-file approvals or per-directory scopes.

*code_exec* is the dangerous one. A sandboxed Python interpreter lets the agent solve, in one call, almost anything you could ask. *Sort this CSV by the third column. Compute the eigenvalues of this matrix. Fit a regression. Make a chart.* Modern coding agents (Claude Code, Cursor's agent mode, OpenAI's Codex, Devin from Cognition) lean on this tool more than any other. The risk is exactly what it sounds like: the agent will sometimes execute code that does something irreversible. The standard mitigation is a sandbox &mdash; a container with no network, no real filesystem outside a scratch directory, no privileges. The standard joke is that agents have been escaping sandboxes since 2023.

*calendar_create* is the one that touches the real world. A web search has no consequences. A calendar invite has consequences &mdash; another human's day. Tools with real-world side effects are usually gated behind explicit per-call approvals (*the model wants to send this invite; do you approve?*). We will come back to the permission ladder in act six.

What you should notice from the right pane is the *shape* of every call. The model thinks in English about whether to call the tool. The model emits a JSON call. The tool returns a structured result. The model reads the result and writes its next thought in English. The English-to-JSON-to-English handoff happens once per tool call, and each handoff is the place where a misunderstanding can creep in. Most of the engineering of a production agent system &mdash; the tool descriptions, the few-shot examples, the validators that reject malformed calls before they run &mdash; exists to make that handoff reliable. The model is brilliant at the English half. The runtime is brilliant at the JSON half. The contract between them, the schema, is the thing that has to be precise.

In the next act we step up one level of abstraction: not a single call, but a tree of calls, organised as a plan.
