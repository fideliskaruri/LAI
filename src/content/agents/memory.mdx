# Three time-scales of remembering

Tap one of the three regions on the left. The top region is *working* memory &mdash; the agent's context window, the actual stretch of tokens the transformer is reading right now. The middle region is *episodic* memory &mdash; a small library of past task transcripts, retrieved on demand. The bottom region is *semantic* memory &mdash; a tiny knowledge graph of distilled facts about the world the agent has accumulated. The right pane explains what the selected memory holds, how it's written, how it's read, and what happens when it fills up.

The three-way split is borrowed wholesale from cognitive psychology &mdash; specifically from the model of human memory that Endel Tulving proposed in 1972 and that has dominated the field since. Tulving was trying to explain why amnesia patients with intact short-term recall and intact general knowledge of the world could still be unable to remember what they had eaten for breakfast that morning. He concluded that the brain has at least three different memory systems running on different time-scales and substrates, and the three of them can fail independently. The names he used &mdash; *working*, *episodic*, *semantic* &mdash; transferred to AI almost without change, because the failures the names describe are exactly the failures language-model agents have. An agent can have a perfectly intact context window (working memory) and still not know what task it was assigned yesterday (episodic memory) or that Rome is the capital of Italy (semantic memory).

*Working memory.* The agent's context window is the most immediate and the most physical memory it has. It is, literally, the stretch of tokens currently in the transformer's attention. For a modern model that might be 200,000 tokens, or a million, or several million. The context is *fully readable* by every layer of the transformer on every forward pass &mdash; that is what attention does. There is no retrieval; the model just sees it. This is the *fastest* memory: it has zero retrieval latency. But it has a hard cap. If the context fills, the oldest tokens fall off the front. (Some systems compress them into summaries before evicting; some don't.) The relevant cognitive analogue is your own short-term scratchpad &mdash; the seven-digit phone number you can hold in your head while you walk to the phone, but that you'll lose if someone interrupts you.

*Episodic memory.* When a task finishes, the agent doesn't keep its transcript in the context window forever. The context is too expensive for that. Instead the transcript gets *written down* to some external store &mdash; today, usually a vector database with embeddings indexed by similarity. When the agent starts a new task, the first thing it does (or that its harness does on its behalf) is *retrieve* a few similar past transcripts and stuff them into the context. The episodic memory is what gives an agent the ability to say *I have done a thing like this before; here's what worked.* It's also what makes agents *learn at all* in the absence of any weight update &mdash; the learning lives in the retrieved transcripts, not in the model. Reflexion, which we'll meet in the next act, lives in episodic memory.

*Semantic memory.* Distilled facts. Not transcripts &mdash; just edges in a graph. *Rome is the capital of Italy. The Roma Pass costs €52 for 72 hours. The user's name is Anya.* This kind of fact is too dense to express as a transcript and too durable to live in the working context. It belongs in a knowledge store that gets queried as needed. Some agents build their own; some agents are paired with a pre-existing semantic store (the company's customer database, Wikipedia, the user's contacts). The retrieval into context is the same shape as for episodic memory &mdash; an embedding query for relevant facts, the top *k* get stuffed in &mdash; but the *granularity* is different. Episodic = whole experiences. Semantic = distilled relations.

I want to flag one subtle thing. All three memories, *in practice*, end up as text in the context window. The context is the only place the model can actually read from. So what differs between the three is not what they *feel like* to the model &mdash; the model reads them all as tokens &mdash; but *where they live when they're not being read* and *how they get retrieved*. Working memory lives in RAM. Episodic memory lives in a vector store, retrieved by similarity. Semantic memory lives in a graph or a fact store, retrieved by query. The retrieval is the engineering. The use, once retrieved, is the same.

The eviction policies on the right pane are worth dwelling on. Working memory evicts on a hard token limit, oldest-first &mdash; if you give the agent 200 turns of context it will, by turn 201, have lost turn 1. Episodic memory evicts almost never; rarely retrieved transcripts are quietly pruned on a slow schedule (or, in practice, just left to rot in the vector store). Semantic memory evicts essentially never; stale facts are corrected, not deleted. (*Rome's mayor isn't who it was in 2018; we add an edge "as of 2026" to the existing node, we don't delete the old node.*) The asymmetry matters. Short-term forgets aggressively because there isn't room; long-term forgets reluctantly because the cost of re-acquiring a fact is high.

There is an unsolved problem here, by the way. The three-way split is a *useful fiction*. In a real production agent you discover that the categories blur. A *plan* you wrote yesterday &mdash; is that working memory (still in context if the task is ongoing), episodic (the transcript of yesterday's planning session), or semantic (the distilled subgoal tree)? In practice it's all three. Engineering an agent's memory system is largely the work of deciding which kind of access pattern you want to optimise for, and accepting that some piece of information will live, redundantly, in two or three stores at once. The fiction is useful because it tells you which knobs to turn when something feels too forgetful or too repetitive.
